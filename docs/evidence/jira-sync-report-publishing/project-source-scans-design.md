# Project source scans

## Decision

Add a local-source SCA scan for a server-owned Project subdirectory. A Project
keeps its long-lived identity and internal scan context; public Engagement APIs
continue to exclude that context. Full quality analysis remains a separate operation.
The user authorized necessary foundation work after the live grouping acceptance
identified this missing producer and access path.

A multi-module SBOM does not prove multiple technical assets: the existing producer
attributes one scan to its canonical source target. The new operation obtains two
real observed assets by scanning two explicitly selected source roots under the
same Project binding. It reuses SCA persistence, inventory generations, attribution,
ticket groups and durable intents. No ProjectAsset table or caller-supplied asset
identity is introduced.

## Contracts

- `POST /api/v1/projects/{key}/source-scans` accepts only `subdirectory` and requires
  the existing operate permission. The server resolves the tenant-owned Project,
  its local source binding and its internal context. Existing local-source policy
  applies. Git/archive selection is outside this operation's initial scope.
- A server-owned `AcquireRequest.ProjectSource` descriptor carries the Project ID,
  approved root and canonical relative subdirectory through the existing queue.
  The request target is the stable original root plus selection; temporary paths
  never become inventory, finding or asset identities.
- The worker reloads the Project binding and context, validates the selection and
  rechecks execution authorization before acquisition or tool execution.
- Acquisition opens the approved root using confined filesystem operations and
  copies only regular files/directories from the selected subtree into a private,
  bounded snapshot before inspecting manifests. Reject symlinks, special entries,
  traversal, cancellation and byte/entry-cap violations; clean temporary files on
  all failures. The approved root and its ancestors remain operator-managed.
- Source jobs have an explicit immutable purpose. Existing full-analysis status
  reads exclude them, including while running; the new job-status route checks
  tenant, Project ownership and purpose. No whole-Project quality snapshot,
  baseline or decoration is generated by a source scan.
- Project-scoped source-finding and ticket routes resolve the internal context
  server-side, then reuse finding/ticket use cases and permissions. Public responses
  and deep links use the Project key, not a hidden Engagement route.
- A focused Project source-findings page reuses ticket preview, linked-ticket and
  observation components. It does not duplicate Engagement governance controls.

## Acceptance

Through normal APIs, scan subdirectories `a`, `b`, then `a` again in one controlled
Project. Real SCA results must bind the same CVE to two distinct observed assets;
rescanning `a` must retain its identity. Confirm the findings through the scoped
human API, preview/submit a grouped restricted Jira ticket on Cloud and DC, and
verify one issue with both asset rows and a working Project finding deep link.
Rescan after a real dependency change and verify update-in-place. Existing quality
analysis status and baseline must remain unchanged. Tests cover hostile paths,
symlink escape/swap, queue round-trip, scope/permission/tenant denial, immutable job
purpose and grouping identity. Contract tests supplement these real runs.

The source-finding list is ID-keyset paginated (default 50, maximum 100); the
single-finding route resolves links independently of the current page. Snapshot
traversal reads at most 128 directory entries per batch, checks cancellation during
copying, and uses confined nonblocking opens with descriptor identity checks.
The API and worker reuse canonical asset attribution under the existing asset
feature flag. SCA findings retain the canonical detector advisory identifier, so
Jira grouping does not infer vulnerability identity from a rendered title.

Project source scans use the existing `sca` queue kind. Stop and drain old SCA
consumers before enabling source-scan admission; do not run mixed versions against
this queue. Older binaries ignore the server-owned selection and purpose fields,
so they cannot preserve the confined snapshot or current-binding checks. Apply
migration 0260 first, then deploy the matching API and workers, and only then admit
source scans.

For rollback, stop source-scan admission first. Drain source jobs with compatible
workers or retain them until compatible workers are restored. Keep migration 0260
and the immutable purpose values while any source records or queued jobs remain;
do not down-migrate, relabel, or hand those jobs to older workers.
